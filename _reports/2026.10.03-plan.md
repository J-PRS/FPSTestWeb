# Audit

## Why the same bugs keep coming back

Your three production killers had one shape: *a timeout/verdict system decided a live player was dead, and there was no single place to check that decision.*

| Failure | Killer | Why it fired |
|---|---|---|
| Anti-cheat kick loop | `moveJudge` | Spawn teleports looked implausible; verdict didn't know about legitimate warps |
| Join throttle lockout | `SessionManager` | Reconnect counted as fresh join against a 30s window |
| Idle reap loop | `tickRecords.reapIdle` | `lastSeen` only stamped by 2 of ~25 message types; `inputMove` didn't count |

The pattern isn't "bad luck" — it's **liveness and session ownership implemented as side effects scattered across handlers**, with at least six independent stores tracking pieces of one identity:

- `ws.data.playerId` (socket tag)
- `room.disconnected` (grace map + timers)
- `specRooms` (spectator index)
- `playerRoom` (room index)
- `SessionManager` tokens + join-throttle map
- `PlayerManager.lastSeen` / `lastPosCheckTime`

Any system can stamp *some* of these; no system owns *all* of them. The idle bug existed because "active player" was defined per-handler instead of once.

## The seven structural problems

### 1. Session lifecycle is implicit — the root cause

`GameServer.onClose` is the choke point, but it only sees socket closes. The things that *cause* closes live everywhere: `SessionManager` has ~10 different `ws.close(code)` sites, `tickRecords` can remove players via `onRemove`, `moveJudge` can kick, `GameServer` runs a 15s join-timeout timer, `RtcServer`/`WtServer`/`RtcRelay` have their own close paths. The stale-socket guard at `GameServer.ts:213` (`connections.getConnection(playerId) !== ws`) had to be *bolted on* after it bit you — that's a symptom of lifecycle being emergent rather than modeled.

**Missing:** a `Session` state machine with named states (`connecting → joined → active → grace → reaped`), one owner of transitions, and a generation number on the socket seat so *no* stale callback can ever mutate a live session — enforced by construction, not by remembering to add guards.

### 2. Transport tiering manufactures the very races it needs grace for

Client `TieredTransport` (380 lines) probes RTC → WT → WS with miss-caching, flap detection, generation epochs, and orphan teardown. Server side, `RtcServer` and `WtServer` adapt channels to fake `ServerWebSocket`s, so one logical player can exist as several sequential or overlapping socket objects. Features like the reconnect-storm guard (`gen` epoch) and the flap breaker exist *purely to defend against complexity the tier layer introduced*.

WS is already the reliable lane every transport falls back to (`ConnectionManager` sends everything reliable regardless), and your metrics showed WT datagrams at ~47% loss. You're paying distributed-systems prices for a throughput optimization that doesn't deliver.

**Verdict:** transport diversity is an optimization being run before correctness. Keep the `GameTransport` interface; reduce to WS-only in production until the session layer is airtight. RTC/WT come back *behind the session layer*, not alongside it.

### 3. `RoomInfo` is a 35-slot callback grab-bag

`MessageHandler` + `RoomInfo` is the real coupling center. Adding flag-knockback required `flagsKnock` plumbed next to `pickupsKnock`, `deployBlast`, `preySplash` — four parallel fields for what is one concept (AOE impulse into physics-enabled objects). Every new cross-domain interaction means: protocol type + validation + handler case + RoomInfo field + Room wiring + sim method + test. That's why Heal Grenade shipped for bots but not humans — the feature matrix lives in *wiring*, not data.

**Missing:** domain event types (`BlastResolved`, `PlayerDied`, `FlagDropped`) that sims subscribe to, versus per-pair callback fields.

### 4. No command queue — messages mutate mid-tick

`handleMessage` mutates authoritative state at packet-arrival time, interleaved arbitrarily with `TickLoop` phases (sims → authority writeback → records → fanout). Determinism currently relies on "the sims don't read the mutated fields at a bad moment" — discipline, not structure. This is also why the `netbot` jitter test flakes: ordering is real-time, not sequenced.

**Missing:** ingress decodes+validates → enqueue per room → tick drains the queue in a defined phase. This one change kills entire classes of timing bugs *and* makes replay testing free (record the queue, replay the queue).

### 5. Two clocks, zero enforcement

`simNow()` vs `Date.now()` is documented in `simClock.ts` but `Date.now()` appears in ~40 server files — `claimLedger`, `shotClaims`, `moveJudge`, `combatBlast`, `respawn`, `PlayerManager` all mix them on the honor system. The idle bug's clock-confusion phase (when I first suspected a sim/wall mismatch) shows how easy this is to misread.

**Missing:** `WallClock` and `SimClock` interfaces injected per subsystem; lint/ownership rule — sims and scenario-driven code take `SimClock`, session/liveness takes `WallClock`, nobody calls `Date.now()` directly.

### 6. `shared/` isn't platform-pure

`process.env` reads in `botHunt`/`botBrain` crashed the browser loop — fixed, but the pattern ("shared code runs on both ends" + "env access is unguarded") is unenforced. One more `process`, `require`, or unseeded `Math.random()` in shared and you get the same crash or silent nondeterminism.

**Missing:** an explicit `SharedEnv`/config param passed in; a bundle check (lint rule: no `process`, `fs`, `Bun` in `shared/`).

### 7. Claims have no uniform acknowledgement

Shots have `shotId` binding + `shotRejected` — the *good* pattern. But `creatureHit`, `deploy`, `heal`, `repair`, `environmentDamage` claims are fire-and-forget; `pendingHits.clear()` on reconnect silently drops them ("predicted hit never confirmed"). The client can't distinguish *rejected* from *transport-lost* from *expired*.

**Missing:** every claim carries a client `claimSeq`; every response is `accepted | rejected(reason) | superseded`, matched by seq. Then your HUD can say exactly what happened instead of a generic timeout.

- **Shared deterministic sims** — `movement`, `projSim`, `ballSim`, `botBrain` replayable on both ends. The edge-event streaming for balls/crawlers (`ballSegment`, `crawlEvt`) is genuinely good architecture.
- **`protocol.ts`** — single definition site, `PROTOCOL_VERSION`, typed unions, `stateHash`/`correction`/`ackSeq` machinery. This is a solid base to formalize, not rewrite.
- **`harness.ts` + scenario tests** — the per-scenario staged-test pattern is right; the problem is coverage gaps in lifecycle paths, not the approach.
- **`ConnectionManager`** is honestly fine — it's `GameServer`/`SessionManager`/`tickRecords` reaching around it that isn't.
- **`tickRecords` interest tiers + suppression** — good bandwidth work, keep.

# What the research says

## 1. Tribes (Frohnmayer/Gift) — our direct ancestor validates the hardest call

Since this game is literally Tribes-style, the original paper is the most relevant source. Their model: **one dumb connection layer that reports packet delivery status, and five specialized stream managers on top** (events, ghosts, input moves, static datablocks, strings) — each with a different delivery guarantee, sharing a single socket.

Two conclusions for us:

- **Their "one transport, many stream guarantees" is exactly what we need** — we instead have three *parallel socket transports* (WS/WT/RTC) each pretending to be the whole connection. Tribes ran unreliable input and reliable events on the same pipe. Our WebTransport datagram experiment (~47% measured loss on loopback — worse than the paper's target hardware!) confirms unreliable lanes aren't paying rent yet. Cutting to WS-first is *more* faithful to the Tribes model, not less.
- **Their transmission-record/notify protocol is my claim-ack proposal** — every packet's delivery status feeds back into the stream managers. We already have this for `tickUpdate` (`ackSeq`); Phase 5 generalizes it to claims. Validated.

## 2. Quake 3 / Source — the command queue and a missed enhancement

Quake 3's model: client sends one `usercmd` per frame; **"the server accepts client commands as they arrive... this is the only time players are ever updated"** — commands are *queued and drained*, exactly Phase 3. Source adds the tick-stamped command + lag-compensation window (`sv_maxunlag` clamps the rewind).

**Enhancement the research surfaces that my plan lacked:** the standard pattern for arrival-timing drift is **server→client clock feedback**. If a client's input arrives targeted at a tick already executed, the server tells it "you're behind, push your command clock forward" rather than silently dropping/reusing. Our `inputMove` has `seq` but no clock-skew correction path — under authority mode a drifting client just has commands reused/stale-dropped forever. Add a `clockHint` server message (or piggyback on `tickUpdate`) reporting the client's queue depth/ahead-behind status.

## 3. Colyseus — our session design is literally their seat-reservation model, plus two details

`allowReconnection`, `_reservedSeats`, `reconnectionToken` as a bearer capability, `checkReconnectionToken` — Phase 1's SessionRegistry maps 1:1 onto a proven framework design. Two refinements worth stealing:

- **`minUptime` (5s default)** — Colyseus refuses auto-reconnect unless the room stayed up ≥5s. This is the exact guard against our reconnect-flap loop: a session that never stabilized doesn't get retried. Add it to the client reconnect policy in Phase 1.
- **`maxEnqueuedMessages` (10)** — during disconnect the client *queues outbound messages* with a cap, flushes on reconnect. We clear `pendingHits` and drop everything; bounded queue-and-flush is strictly better for claims that mustn't be lost (deploy, chat, classUpdate).

Also: their reconnect token is **rotated after each successful reconnection** — ours persists. Rotate-on-reconnect is cheap and kills stale-token replay.

## 4. NSDI 2025 browser-networking evaluation — WS is the right baseline

The academic comparison confirms the transport ranking we assumed: WS = simple reliable ordered (head-of-line blocking under loss), RTC DataChannel = UDP-like semantics but heavy multi-layer processing overhead, WebTransport = best theoretical fit but narrow/immature support. For a correctness pass on a small player count, WS-only is the defensible baseline; the unreliable lanes matter only once player counts and tick rates make HOL blocking measurable.

## 5. Determinism: Gaffer confirms our hybrid is right, and bounds it

Deterministic lockstep is recommended **≤4 players only** — our shared sims aren't lockstep, they're *server-authoritative replays* (balls/crawlers via edge events, which is the Tribes "ghost event" model). That's the right side of the line. But the `stateHash` mismatches we already see are Gaffer's predicted "approximately-same" prediction divergence — expected, and Phase 3's recorded-command replay is the standard fix for distinguishing divergence from true nondeterminism.

# Revised plan — what changes

Phases stand; the research adds these to specific phases:

**Phase 1 additions (Session):**
- Reconnect token **rotated per reclaim**, single-use reservation consumption (Colyseus model).
- Client-side **`minUptime` gate** — no auto-reconnect for a session that never lived ≥5s; kills flap loops by policy not just backoff.
- **Bounded outbound queue during disconnect** (~16 commands) flushed on reclaim, so `deploy`/`chat`/`classUpdate` survive a blip instead of `pendingHits.clear()`.

**Phase 3 additions (Commands/clocks):**
- Server reports **command-queue timing feedback** (client ahead/behind → nudge its send clock), the Quake/Source pattern — prevents slow-drift staleness in authority mode.
- Recorded command streams double as **replay files** — feeds Phase 7 determinism tests for free.

**Phase 5 refinement:**
- Generalize the existing `ackSeq` into a Tribes-style **transmission-record layer**: reliable-ordered stream (events, claims, rosters) vs unreliable-unordered stream (moves, input) *as message classes*, transport-agnostic. On WS the unreliable class degrades to "drop stale seq server-side" — same code, no HOL cost since each input supersedes the last.

**New Phase-1 acceptance criterion from research:** reconnect flow must survive the exact Colyseus sequence — drop → retry w/ backoff → reclaim → resume listeners — including page-reload (manual token path).
