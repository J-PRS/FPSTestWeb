Researched it — and the honest headline is: **your architecture is already the canonical one.** `TrailBatch` (one merged geometry, 512 fixed ribbon slots, generation-tagged handles, dirty-range uploads) is exactly what the references prescribe. The fights you're having are almost certainly the *ownership/bookkeeping* layer, not the mesh tech. Here's what "proper" looks like per the sources, mapped against what you have:

## 1. The trail itself — strip, not quads

Canonical approach (Stride docs, mkkellogg/TrailRenderer, verekia's r3f trail, quarks):

- Sample the head into a **ring buffer of fixed capacity** — position + frame basis. Sampling should be gated by **minDistance + sampleRate**, not every frame — otherwise trail length/density is framerate-dependent.
- Build **one strip** connecting samples — two verts per sample, triangles between adjacent pairs. UV.v maps to sample age so width/alpha fade is a texture ramp or attribute, not CPU work.
- Ribbon vs trail distinction (Stride): **ribbon = camera-facing** (recomputes every frame), **trail = fixed axis** (stable, cheaper, no twist artifacts when the camera orbits). Most projectile trails want camera-facing; sword swings want fixed.

## 2. Buffer discipline — the non-negotiables

From the three.js manual + mozvr particle-recycling article:

- **Never resize a buffer at runtime.** Pre-allocate the max, use `setDrawRange`. ✔ yours
- `usage = DynamicDrawUsage`, set `needsUpdate` only when dirty, and use **`addUpdateRange`/`updateRange`** to upload only the changed slice — never re-upload the whole buffer. ✔ yours
- Ring-buffer cursor writes: you don't rebuild the strip, you just overwrite the oldest slot. ✔ yours

## 3. Pooling — where the "fundamental" bugs live

Standard pool contract (and your AGENTS.md already names the failure modes):

- **Fixed-capacity free-list**; overflow creates a *second batch*, never grows the hot one. ✔ you have `claimableBatch`/batch lists
- **Generation counters** on every slot so a stale handle can't resurrect or double-release. ✔ `owns(slot, gen)`
- **Single-owner handles**: owner calls `stop()`, keeps ticking until `done`, then `dispose()` — and a path that bypasses `release` leaves a lit slot forever (your `litAudit`/`sweepLit` is the right auto-heal for exactly this).
- **Teleport is explicit, never implied**: a jump > ~0.25s of travel must `clear()`/`teleport()` — otherwise the strip draws a chord across the map (your `push()` chord-refusal is the right guard).
- Pool what churns; don't pool what doesn't. And don't shrink the pool the moment load drops — thrash between grow/shrink defeats the point.

## 4. The common failure modes (what "done wrong" looks like)

- New `BufferGeometry`/material per projectile per frame → GC stutter + `bufferData` storms.
- Re-expanding ribbon verts on CPU each frame for every trail — O(trails × samples) CPU; the modern approach (quarks `RibbonTrail`, plume, nachi) pushes per-point data once and expands width/facing **in the vertex shader** via a `side` attribute.
- Per-trail scene objects (each `Mesh` = a draw call + a cull pass + disposal bookkeeping) vs the merged batch you have.
- Sorting trail samples by *age* instead of *spawn order* — ages change every frame, order doesn't (Stride calls this out explicitly).
- Ownership ambiguity: handle released by teardown while an owner still pushes → the "zombie slot" your `fxDiag` watches for.

## Recommendation

Since the batch is sound, the fix direction isn't a rewrite — it's a **contract audit**: every trail-owning entity (projectile, jetpack, disc, sword) checked against `stop → update-until-done → dispose`, `teleport` on respawn/impact, and no handle shared across owners. The Alt+Q fields (`slot=-1`, `zombiePushes>0`, unowned lit slots) already measure exactly this — the bug hunt is "which owner violates the contract," not "is the batch right."

If the fights are *visual* (twisting, popping, thin at angles) rather than lifecycle, that's the camera-facing math — the fix there is quarks-style shader expansion with a stored per-sample view axis, not more CPU work.
