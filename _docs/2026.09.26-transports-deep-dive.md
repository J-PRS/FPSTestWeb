# Transport Deep Dive — TCP / UDP / QUIC for a Browser FPS

Reference doc, 2026-09-26. Covers the wire protocols, the browser APIs that
expose them, real pricing for a mid-size workload, and what it means for
this codebase. Sources: NSDI'25 browser-networking paper, Krunker packet
format (krunker_packet_core), T1/T2 engine networking model +
AltimorTASDK/TribesRebirth (leaked Darkstar source), growordie MMO
writeup, Pelican Party (Narrow.one) interviews.

## 1. The two layers nobody separates

**Layer 1 — wire protocols** (what packets actually ride on):

| | Reliability | Ordering | Congestion control | Head-of-line block |
|---|---|---|---|---|
| TCP | Retransmit until delivered | Strict FIFO | Throughput-optimized (CUBIC) | YES — one lost segment stalls all queued data |
| UDP | None | None | None — app must manage | No |
| QUIC | Both modes in one conn | Per-stream | BBRv1, latency-tuned | No — independent streams + datagrams |

**Layer 2 — what browser JS is allowed to touch:**

| API | Layer 1 under it | Unreliable send? | Notes |
|---|---|---|---|
| `fetch`/XHR | TCP (H1/H2/H3) | no | Request/response only |
| **WebSocket** | TCP | **no** | The only persistent bidirectional pipe with universal support |
| **WebRTC DataChannel** | UDP + DTLS + SCTP | yes (`unordered`/`unreliable`) | Built for P2P: requires ICE/STUN/SDP negotiation; server-side you host the full DTLS/SCTP stack yourself. Heavy machinery for client-server |
| **WebTransport** | QUIC (HTTP/3) | **yes** — `sendDatagram()` + reliable streams | Chrome/Edge 97+, Firefox landing, Safari partial. Server: quiche/msquic/quic-go; **Bun: not stable yet** |
| Raw TCP/UDP sockets | — | — | **Not exposed to browser JS, period.** No exceptions |

Key fact: a browser game literally cannot send a UDP packet. Every
"UDP-feeling" browser game is WebRTC or WebTransport. Krunker = WebSocket.
Narrow.one = WebSocket. Us = WebSocket.

## 2. Why TCP hurts (and when it doesn't)

The NSDI'25 measurements, distilled:

- **Head-of-line blocking**: position update #47 lost → #48..#52 sit in the
  receive buffer while TCP retransmits #47. Stall ≈ 1 RTT + loss-recovery
  (~200ms worst case). Since #47 is *superseded* by #48 anyway, the stall
  buys you stale data — paying latency to deliver garbage.
- **TCP congestion control is throughput-shaped**: after loss it halts
 /halves and ramps — fine for file downloads, wrong for fixed-rate game
  ticks. QUIC's BBR is latency-first.
- **BUT**: under clean links (<1% loss, typical broadband/Wi-Fi),
  measured RTTs for WS vs WT were within single-digit ms. The pain is a
  tail phenomenon — bad Wi-Fi, congested routes, mobile handoffs.

Why it doesn't kill us today: our interp delay (120ms) + Hermite
spline + 250ms extrapolation cap + dead-reckoning absorbs most
retransmit stalls. A 200ms HoL stall hits right at the buffer edge —
that's exactly when remotes visibly snap. It happens, it's just rare.

## 3. QUIC/WebTransport — the actual shape

A WebTransport session = one QUIC connection carrying:

- **Datagrams** (`sendDatagram`, unreliable, unordered, no retransmit) —
  the UDP lane: `position` reports, `tickUpdate` broadcasts. Stale data
  dropped by design.
- **Unidirectional streams** — reliable ordered, no response needed:
  scoreboard pushes, kill feeds.
- **Bidirectional streams** — reliable ordered request/response:
  join handshake, demo upload could stay plain HTTPS.

This is *literally* the T2 stream-manager architecture (Event / Ghost /
Move lanes with different reliability) reborn as an IETF standard. The
Tribes paper's insight — "different data needs different delivery
guarantees" — is now a checkbox in a browser API.

Blockers as of writing: Bun.serve has no stable WebTransport; Firefox
support is in-progress; Cloudflare quick tunnels / surge can't carry it.

## 4. WebRTC — why nobody picks it for client-server

Technically gives you unreliable UDP semantics in every browser today.
But it's built for *peer-to-peer media*: establishing a session requires
ICE candidates, STUN, SDP offer/answer — handshake machinery designed for
two browsers finding each other through NATs. Running it client-server
means hosting pion/aiortc and bolting on signaling yourself. Every team
that tried reports weeks of plumbing for marginal gain over WS. Skip it.

## 5. What the reference games actually do

**Krunker** (browser FPS, 30k+ CCU): WebSocket + msgpack. Hot packets are
positional arrays — `["k", 42, 1.0, 5.0, …]` — not objects. Client-side
prediction is default-on (KrunkScript exposes `disablePrediction()`).
Server authoritative for health/score only. **The lesson: they won on
bytes-per-packet, not transport.**

**Narrow.one** (5v5, millions of plays): Three.js + custom WS backend on
$4/month DigitalOcean boxes, ~200 players/box. Architecture is
deliberately boring; the whole game is ~1MB of assets.

**Tribes 1/2**: raw UDP, 32ms ticks, five stream managers (Event=guaranteed
ordered, Ghost=most-recent-state, Move=input stream, Datablock, String),
per-ghost scoping, packet-delivery notification protocol for acking.
client prediction via the control object + last-acked-move echo +
reconciliation — the pattern every modern shooter uses.

**Altimor's netXT** (T1 retrofit): synced clock off server tick embeds,
48ms timeNudge, ghosts run the real `updateMove`, position-only lag-comp
rewind (250ms cap), subtick trigger pulls, prediction-keyed projectile
adoption. See `2026.09.26-T1.md`.

## 6. Pricing — the part people get wrong

**Egress is billed per byte. The protocol is irrelevant to the invoice.**
The costs hide in infrastructure and CPU.

### Workload model (from our earlier math)

1,000 players/day × 3×20min = 30,000 player-hours/month, ~31 concurrent
16v16 matches, 20Hz tick:

| Wire format | Downstream/player | Monthly egress |
|---|---|---|
| JSON objects (~150B/player/tick) | ~93KB/s | ~10 TB |
| Packed binary (~30B/player/tick) | ~19KB/s | ~2 TB |

### Per-protocol total cost (same workload)

| | TCP / WebSocket | Raw UDP | QUIC / WebTransport |
|---|---|---|---|
| VM | €10 Hetzner (20TB incl.) | €10 (can't reach browsers) | €10 box works, UDP/443 inbound |
| Managed LB | Everywhere, $10-20 | L4 UDP LBs: rarer, pricier | **Essentially DIY** — no cheap managed QUIC ingress for games |
| Server CPU | Kernel TCP, ~free | ~free | **~2-3× per-conn CPU** — QUIC crypto + BBR run in userspace (quiche/msquic benchmarks) |
| TLS | Optional or cheap (Caddy/nginx) | DTLS if encrypted | Mandatory QUIC-TLS, cert renewals on you |
| DDoS shield | **Cloudflare free** — WS proxies through it | Spectrum = enterprise $$ | Spectrum = enterprise $$ |
| Tunnel/CDN reach | trycloudflare/surge/everything | none | HTTP/3 to browsers, but **not WebTransport** on free tiers |
| Browser reach | Universal | n/a | Chrome/Edge only today |

### The two real cost drivers

1. **Bytes** — wire format (Phase 3b) is a 5× lever on the only metered
   resource. 10TB→2TB. On Hetzner both fit the included pool anyway.
2. **DDoS economics** — game servers get attacked out of spite. WebSocket
   behind Cloudflare/surge = free absorption. UDP/QUIC = you're exposed on
   a raw IP or paying enterprise filtering. This alone has kept several
   io-games on WS even after QUIC matured client-side.

### Total for the imaginary workload

- **Today (WS+JSON)**: ~€10/mo Hetzner / ~$85 DO / ~$950 AWS
- **Binary hot path**: ~€10 Hetzner / ~$12 DO / ~$230 AWS
- **WebTransport**: same VM, +CPU headroom needed, −protection unless
  Spectrum, −tunnels, −Firefox users. Net: *more* expensive to run
  safely, for a latency tail improvement on dirty links only.

## 7. Where that leaves us

- **WebSocket/TCP is the correct transport now** — universal reach,
  free DDoS absorption, kernel-cheap. Krunker/Narrow.one scale on it.
- **The money lever is bytes, not protocol** — Phase 3b binary codec.
- **The architecture reason for Phase 2** (Socket.ts isolation) is that
  WebTransport becomes a one-file swap when Bun + Firefox + tunnels catch
  up. Collapse now, swap cheaply later.
- **Watch items** (revisit triggers): Bun stable WebTransport server;
  Firefox ships WT; Cloudflare tunnels carrying HTTP/3 datagrams;
  player reports of rubber-banding correlating with lossy links.
- If QUIC day comes: datagrams carry `position`/`tickUpdate`, reliable
  streams carry hits/joins/kills — the doc's protocol split already
  assumes this seam.
