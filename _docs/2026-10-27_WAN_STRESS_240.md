# WAN stress — 240 bots × 10 rooms on live OCI (2026-10-27)

What the production box does at 10× match density over real `wss://`,
measured live with per-2s resource sampling. Answers the "how does it
bend" question that loopback soaks can't.

## Method

- **Driver**: `_tools/devin_scratch/_wide.ts` — 10 rooms × 24 bots,
  link quartiles rotated across the roster (40ms → 250ms+150jit+3%loss),
  `bun tests/netbot/soak.ts`-style real `NetClient`/`NetBot` stacks.
- **Join pacing**: 3.4s between connects (~17.6/min) — the server's
  20/min/IP flood guard **kills** a socket with `1013` above it and the
  netbot join-retry is same-socket resend only, so a flood-guard death
  is permanent. Pace is the whole trick on a shared-IP fleet.
- **Cap**: `FPS_GLOBAL_MAX_PLAYERS` bumped 128→256 in `~/kribes/.env`
  + `server.env` (env-tunable, restart sourced explicitly).
- **Monitor**: ssh-held remote loop — `top -bn1 -p <bun>` + `ss -tn`
  counts + `/proc/net/dev` enp0s6 deltas, 2s cadence → `~/mon_stream.csv`.

## Results

**Join phase**: 240/240 connected in 888s (~14.8 min) — flood-guard
shaped the ramp as designed; re-armed retries seated every bot, no
ghosts. `join throttle` doing its job is *the* WAN-join answer.

**Combat (90s simultaneous)**:

| metric | value | verdict |
|---|---|---|
| rooms live | 10/10, 24 gameStates each | ✅ no silent seats |
| tick frames delivered | 2,526,804 total | ✅ |
| kills / hits | 66 / ~760 | ✅ real combat |
| corrections | **0 on every client** | ✅ no prediction breaks |
| claim rejects | 13 (dead-shot races, 66 deaths) | ✅ legal class |
| ghost joins | 0 | ✅ |

**Resource shape** (the point of the exercise):

| | idle | peak | reading |
|---|---|---|---|
| CPU | ~0% | **~187%** (1.9/4 cores) | join-burst > combat — handshake + roster serialize is the hot phase |
| RSS | 68MB | ~720MB | ~2.4MB/conn amortized; GC reclaimed to ~190MB post-teardown |
| TX | — | ~660 KB/s ≈ 5.3 Mbps | 20Hz fanout at 240 sockets |
| RX | — | ~240 KB/s ≈ 1.9 Mbps | claims + position uplink |
| Established TCP | ~10 | ~720 | 240 ws + ~240 HTTP keepalive (field-fetch lane) + base |

**Post-teardown**: sockets → ~11, CPU → 0% in ~30s, RSS draining through
GC. No leak state, no lingering game objects.

## Findings

1. **The join ramp is the expensive phase, not steady state.** CPU peaked
   during connect-burst (roster serialize + handshake + first
   gameState), then settled lower during combat. A real launch-day
   connect storm is the load to design for.
2. **The map-fetch HTTP keepalive lane doubles the socket count** —
   every bot holds ws + an HTTP keepalive for `/maps/*.bin`. At scale
   that's a second per-client fd. Worth knowing for conn-limit math.
3. **~2.4MB/conn RSS is the real cost model** at this shape (ticks +
   buffers + roster per room); GC is healthy — memory returns.
4. **Zero corrections at real WAN ping** — the prediction/correction
   loop is genuinely quiet on a live path, not just on loopback.
5. **240 conns ≠ 240×20Hz × 4 cores**: 1.9 cores at the ramp apex, which
   is ~4× what a single 32-player room costs — the multi-room fanout
   shares one event loop and the aggregate is the number that matters.

## Caveats

- `closed=24` per room is a teardown artifact (driver closes before
  printing) — wire the closed-check pre-teardown next run for the
  reclaim/recovery signal.
- Reject reasons weren't decomposed — 13 is the dead-shot class by
  arithmetic (66 deaths, ~1 in-flight race each) but the reason map
  wasn't dumped.
- RSS partly holds the HTTP keepalive fleet, not pure game state.
- Single vantage (my link) — regional variance untested.
