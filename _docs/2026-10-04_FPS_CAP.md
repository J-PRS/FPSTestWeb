# FPS Cap — what it is, what it isn't, and the 30Hz-sim question

2026-10-04 · client-side render pacing analysis

## How the cap works today

`fpsCapAllows` (gameLoop.ts) accumulates real elapsed time and only lets
`renderFrame` run once per `1/cap` seconds — **render-skip only**. The
loop itself (sim, input, FX, HUD, netcode) still runs at every rAF tick,
which is vsync-locked to the display.

```
rAF (60/120/144Hz — display locked)
 ├─ simTick        always
 ├─ fxTick         always
 ├─ hudTick        always
 └─ renderFrame    only when renderAcc ≥ 1/cap
```

So "FPS CAP: 30" means *render at 30*, not *run at 30*.

## The lying meter (fixed)

Both FPS readouts counted **loop ticks**, not renders — at CAP 30 they
still read 60 because the loop kept firing:

- `HudStats.updateFps` ran inside `tick()` every rAF. Now driven by
  `HUD.markFrame(renderElapsed)`, called only when a render lands, fed
  the real accumulated time between presents.
- The stats.js debug panels (backquote) had the same bug — `s.update()`
  counts calls as frames; moved inside the render branch too.

The MS panel now correctly reads ~33ms at cap 30 (render-to-render gap)
instead of ~16ms loop time.

## Does the game know the monitor's refresh rate?

No — and browsers offer no API for it (`screen.refreshRate` doesn't
exist). The only honest signal is rAF cadence itself: measure the median
rAF delta over ~30 frames at boot, snap to the nearest common rate
(60/75/90/120/144/165/240). `loopPerf` measures *achieved* frame time for
auto-quality, but that can't distinguish "144Hz panel struggling at 90"
from "90Hz panel" — a dedicated boot measurement could.

## Is the feature useful?

**Real:**
- GPU savings are genuine — skipped renders halve raster/shadow/post
  work (the weak-iGPU + battery audience)
- three.js render-side JS (scene traversal, draw calls) is skipped too —
  real main-thread relief
- Gives the auto-quality ladder honest headroom numbers

**Nonsense:**
- Sim/input/netcode/FX still tick every rAF — a sim-CPU-bound machine
  gets nothing
- Caps above the panel rate are dead options (rAF can't beat vsync)
- On non-60Hz panels the accumulator produces an uneven beat: cap 30 on
  a 144Hz display renders every ~4.8th tick — ~30fps with micro-judder

## Could the whole sim run at cap rate?

Mostly yes — the codebase is dt-driven, and projectile tunneling is
already solved properly (`sweep.ts`: swept-sphere + bisected terrain
crossing + closest-approach wake checks — no per-frame point tests).
The real costs:

| System | At 30Hz | Verdict |
|---|---|---|
| Mouse look (in `player.update`) | +16ms aim latency | **Keep at rAF** — the one thing users feel |
| Movement sim (shared) | Correct but grainier ski/bounce | dt-safe, subjective |
| Client prediction journal | Coarser steps; server is 20Hz anyway | fine |
| Creatures/bots/projectiles | dt-driven, already staggered | free win |
| FX decay, audio, HUD | wall-clock already | free win |

**Recommended shape** (not implemented): two accumulators — world sim
on the cap, input+camera at rAF. Gets ~80% of the CPU saving with none
of the aim-feel cost. The all-in version (simTick gated wholesale) is a
one-accumulator experiment worth trying — just keep mouse sampling out
of it.

## Related knobs

- `fps-cap` setting: `[0, 30, 60, 120]` — could gain a measured "native"
  entry or gray out options ≥ panel Hz once rAF measurement exists
- `MAX_DELTA_TIME` clamps sim dt — already protects big-step stability
