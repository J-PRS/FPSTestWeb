## What Altimor's netXT does

**1. Clock sync — the foundation.** Server embeds its tick count in every packet; client keeps a `syncedClock` offset plus a rolling error history, and nudges its clock when average drift exceeds `clientClockCorrection = 8ms`. Everything downstream — interpolation, subtick, lag comp — gets a shared timeline.

**2. Fixed `timeNudge = 48ms`** — interpolation offset on a 32ms tick = ~1.5 ticks of render delay.

**3. Ghosts run the *real* physics.** Remote players aren't visually lerped — `clientMove` runs actual `updateMove` per missing tick using `lastPlayerMove`, then `loadSnapshotInterpolated(curTime)` renders the sub-tick interpolated pose. Dead reckoning literally IS the same movement code as local prediction. Snapshots land in a ring buffer (`SnapHistory = 1s`), newer predictions get `invalidatePrediction`'d and re-simulated. After `ghostTimeout = 250ms` silence, the ghost snaps back to last server position and freezes.

**4. Server-side lag compensation.** Each client move carries a `writeLagCompensation` timestamp = the client's *render time* (syncedClock − timeNudge − subtick adjust). Server clamps it to `maxLagCompensation = 250ms` and, during `serverProcess` for bullets/rockets/grenades, rewinds every other player's **position only** (`loadSnapshotPositionOnly`) into `lagCompensationSnapshots` — hit detection against the world exactly as the shooter saw it.

**5. Subtick — CS2-style, in 2002.** Trigger pulls record a 1–32 subtick offset + the pitch/yaw at that instant. Server replays the tick, then warps the shooter to the *interpolated subtick position*, fires with exact subtick aim, then restores. 

**6. Predicted projectile adoption.** Client spawns its projectile instantly with `predictionKeyXT = moveCount`. Server echoes the key in the ghost; on arrival the predicted projectile is *returned as the authoritative ghost* — zero flicker, no respawn. Mispredictions get culled. Spread uses `Random(predictionKeyXT)` — deterministic seed, client visual = server truth exactly.

**7. Predicted weapon state** — ammo/fire/trigger snapshots keyed by moveCount; ammo estimated client-side (energy > minEnergy).

## Mapping to our stack

| His technique | Our equivalent | Verdict |
|---|---|---|
| Clock sync (shared server timeline) | Snapshots keyed by **arrival time** | **Biggest gap.** Jitter distorts snapshot spacing *and* our Hermite tangents. Stamping updates with server tick → local-time mapping is the clean fix our adaptive delay currently approximates |
| `timeNudge` 48ms fixed | Adaptive 100–300ms | Ours is better for the internet — his assumes LAN-ish |
| Ghost runs real `updateMove` | Simplified `simulatePhysics` | Worth porting: reuse `MovementController` on dead-reckoning remotes so DR trajectory matches real physics (skiing, slope effects) |
| Lag comp rewind, position-only | Server uses positions as-of server time | **Real hit-reg improvement** — rewind victims by shooter's render delay during `serverProcess` on explosions/disc hits. We're already 80% there (position history exists) |
| Subtick (ms offset + aim at fire) | Shot events, tick-quantized | Cheap version: attach ms timestamp + send-time aim to `playerShoot` events |
| Prediction-key adoption | `pendingLocalProjectiles` linked by server ID | Equivalent already — ours links after roundtrip, his adopts instantly. Marginal gain |
| Seeded spread RNG | — | If predicted vs server projectile visuals ever diverge |
| `applyAccumulatedAim` | Per-frame mouse | Check ours — if yaw is only sampled per send-tick, applying accumulated mouse per-frame is free latency |
| Ghost timeout → freeze at 250ms | DR forever | Ours is more forgiving; his is stricter but safer (no flying corpses) |

## The steal-worthy insight

His core architectural bet is different from ours: **run the same tick code on both sides and let the server feed corrections into a shared snapshot history**, rather than *simulate locally + smooth visuals*. His remotes aren't "smoothed displays" — they're re-simulated entities corrected backward. That's why his netcode feels so crisp: every entity, local and remote, is on the same simulation rails, and the interp buffer is a *resimulation window*, not a render offset.

That's a bigger refactor than our current snapshot-interp approach — but the concrete wins to cherry-pick without the rewrite:

1. **Clock sync** — highest value, medium effort. Server timestamp → client maps to server-time domain → interp buffer spaces snapshots on the *true* timeline.
2. **Real physics DR** — swap `simulatePhysics` for a `MovementController` tick on dead-reckoning remotes. Trajectory stops diverging at slope edges/skiing.
3. **Position-only lag comp** on the server — rewind victims during `serverProcess` explosion/disc checks by ~½RTT + render delay.

Want me to pick one? Clock sync is the architecturally-correct fix for the jitter problem our adaptive delay is papering over.
