Good research topic — there's a real list. Ranked by effort/payoff:

**Probably free wins:**

1. **Check `permessage-deflate` is off.** If Bun's ws negotiates compression, every message pays zlib latency for compression ratio you don't need (your 39B binary frames gain ~nothing). Deflate also has a history of CPU/memory problems on Node `ws`. Explicitly disable server-side.
2. **Verify TCP_NODELAY is set.** Nagle's algorithm queues sub-MSS packets waiting for ACKs — the classic "why is my 20Hz stream arriving in clumps" bug. uSockets (Bun's ws engine) sets it by default, but worth a `ss`/`netstat` check on the live socket to confirm.
3. **Only send whole, latest packets.** With NODELAY every `send()` = a TCP segment, so never send a header + body separately — you already batch tick updates, just don't regress.

**The real one: `bufferedAmount` backpressure**

This is the fix that matters most for lossy-connection players:

- `ws.send()` **never fails** — a slow/flaky client's unacked data piles into an *unbounded userspace queue*. The pipe fills with 20Hz *stale* positions; the player receives ghosts from 500ms ago even after the connection recovers. The backlog drains chronologically, so lag compounds instead of self-healing.
- The fix: check `ws.bufferedAmount` (client) / `ws.getBufferedAmount()` (Bun server-side — you already have a `drain` handler stub). When it crosses a small watermark (~64KB), **stop enqueueing position updates entirely** — drop them, don't queue them. When it drains, resume with the *latest* state only. TCP then guarantees the receiver gets mostly-fresh state instead of a fossil record.
- Do the same client→server: if `socket.bufferedAmount > threshold`, skip that input send — the next one supersedes it anyway. This is the WS-native way to get 80% of UDP's "drop stale state" benefit.

**Adaptive interpolation buffer**

Classic netcode: don't run a fixed render delay — size the interp buffer to measured jitter. You already collect jitter telemetry (`getJitter`). Buffer = `tick interval + ~2× jitter`, clamped 50–250ms. High-jitter players trade a bit of delay for smoothness instead of stuttering through buffer underruns.

**Send-side**

- **Adaptive tick rate per client** — a socket with rising bufferedAmount drops to 10Hz for *non-critical* updates while events stay 20Hz. A struggling connection gets less work, not a bigger queue.
- **Event-vs-state split is already right** — shots/hits as ordered events (where TCP ordering helps), position as supersedeable state. The anti-pattern is sending *every* projectile position every tick — only muzzle + fuse travel the wire.

**Not worth it on TCP:**

- Redundant last-N-inputs piggyback (helps UDP, meaningless on an ordered stream)
- Delta compression beyond your suppression (saves bytes, not latency — you don't have a bandwidth problem)

The actionable short list: **kill permessage-deflate, confirm NODELAY, add bufferedAmount watermarks on both ends, adaptive interp buffer from your jitter metric**. The bufferedAmount piece is the closest thing to UDP semantics you can get while staying on WebSocket — it's literally "drop superseded state" implemented at the application layer.
