# Bots as legal players — implementation plan

Goal: a bot is a **virtual client**, not a scripted prop. Its brain produces
the same *inputs* a human sends (move keys, aim yaw/pitch, weapon choice,
fire, belt, skills) and the same shared sims produce motion/damage. If a
bot can do something a player legally can't, that's a bug in the wiring —
not a bot feature.

## Current state (what exists today)

- `shared/botBrain.ts` — `BotBrain.think(dt, ctx) → { dest, fire? }`.
  Already shared between client `GameBot` and server `ServerBots`.
  Emits a *destination point* + optional fire command. Has LOS checks
  (heightfield), context steering, position-picker combat, flinch,
  personality scalars.
- `shared/movement.ts` — `MoveSim`: the full player physics (ground
  accel/friction, jump/autohop, air control, ski friction toggle, jet
  thrust, terrain collide). `MoveInput = {forward, right, jumpPressed,
  jumpHeld, skiHeld, jetHeld}` + state yaw/pitch. Fixed-step 60Hz.
- `server_bun/src/RoomMoveSim.ts` — per-player `MoveSim` shadow fed by
  `inputMove`, energy economy (jet drain, skill antes/drains from STATUS
  bits), seq ordering, reconcile→correction. **This is already "a virtual
  player body" — bots should reuse it, not fork it.**
- `server_bun/src/ServerBots.ts` — bots are real `PlayerState`s in
  PlayerManager (hit claims, knockback, deaths, respawn, tick fan-out all
  reuse player machinery). Locomotion is a custom ground-clamped walk —
  THIS is the stub to delete.
- `shared/combat.ts` — `validateHitClaim`/`validateAoeClaim` against
  `TrackedProjectile`; `aoeDamage`/`aoeImpulse`; `pointToCapsuleDistance`.
- `shared/weapons.ts` — `WEAPONS` stats table: speed, gravity, damage,
  aoeRadius, refire cadence, directDamage, hitGrow, pellet counts, etc.
- `server_bun/src/CombatHandler.ts` — `handleShot` (hit claims vs tracked
  projectiles + lag rewind), `processAOE`, `botAttack` (hitscan), the
  projectile registry (`projectileCreated`/tracking).
- `client/src/game/botBrain.ts` — `GameBot extends RemotePlayer`;
  `localDriven = true` (bypasses snapshot interp — position is written
  directly), `botVel` local physics. `takeDamageLocal` is the offline
  authority path.
- `client/src/game/bots.ts` — `TeamBots` referee: roster, teams, scoring,
  CTF glue, watchdog.
- Shared bot energy/jet economy already exists inside `RoomMoveSim`
  (Shadow.energy/jetDrain/jetRegen/skillDrain from STATUS bits).

## Architecture

```
                    ┌──────────── BotBrain (shared) ────────────┐
                    │  utility goals + context steering          │
                    │  OUTPUTS: MoveInput + aim + fire + belt    │
                    └──────────────┬─────────────────────────────┘
                                   │
        ┌──────────────────────────┼───────────────────────────┐
        │ server (ServerBots)      │ offline (GameBot/TeamBots) │
        ▼                          ▼                            │
  RoomMoveSim shadow          a local MoveSim (client-side      │
  (MoveSim + energy model)    wrapper like MovementController)  │
        │                          │                            │
        ▼                          ▼                            │
  PlayerState.position/vel    RemotePlayer.position (localDriven)│
        │                          │                            │
        ▼                          ▼                            │
  normal tick fanout          rendered directly                 │
```

The brain stops returning a position destination. It returns **inputs**:

```ts
export interface BrainOut {
  input: { forward: number; right: number; jump: boolean; ski: boolean; jet: boolean };
  yaw: number;             // desired facing — sim needs it for input dir
  fire?: { weaponType: number; aim: BotVec; targetId?: string };
  belt?: 'disc' | 'grenade' | 'mine' | 'health';  // belt slot use
  skill?: 'cloak' | 'shield' | 'mend' | null;     // toggle intent
}
```

`dest` stays internal to steering — the *output* is a heading turned into
forward/right relative to yaw, plus ski/jet/jump flags. This is the core
change: brains write intents, sims own truth.

## Phase 1 — Movement through MoveSim (the "legal body")

**Server side.** A bot already has a shadow in `RoomMoveSim` — wire it:

- `ServerBots.populate` → also `room.moveSim.track(id, pos, yaw)` (and
  `untrack` on retire). Bot shadows get the same energy model for free.
- Each tick, run the brain → convert to `moveSim.setInput(id, {
  forward, right, jumpPressed, jumpHeld, skiHeld, jetHeld }, status, seq)`
  with a local incrementing seq — the existing seq gate works unchanged.
- Commit: `moveSim.simState(id)` → `p.position`, `p.velocity`,
  `p.rotation.yaw`. Exactly what authority-mode ticks do for humans;
  bots just never send `position` reports so `reconcile` is skipped.
- STATUS bits: set `ski`/`status` on the PlayerState so clients render
  ski dust and skill auras on bots like real players.

**Client/offline side.** `GameBot` gets a `MoveSim` instance over a
`TerrainSurface` adapter (same wrapper as `MovementController`) and a
local energy model (mirror `RoomMoveSim`'s fields or extract the energy
economy into `shared/` so both use one copy — **do extract it**:
`shared/energy.ts`, imported by RoomMoveSim and the client bot path).
`think()` drives `sim.setInput` + `sim.update(dt)`, then writes
`state.pos` into `this.position` (localDriven already bypasses interp).

**Brain changes** (`shared/botBrain.ts`):
- `steer()` currently returns a destination → instead return a *heading
  vector*; the caller-facing `think()` converts heading+desired-facing
  into `{forward,right}` in bot-yaw space and sets `yaw` toward heading
  (or toward the hunt target when firing — aim yaw vs move yaw can split,
  which humans do anyway).
- Ski/jet policy: `skiHeld` when moving downhill or >8m/s; `jetHeld` for
  uphill escapes, reaching objectives on ridges, and pursuit of airborne
  targets; `jump` on steep uphill stalls (replaces/complements detour).
- Keep LOS/steering/flinch/personality — they're already the good part.

**Yaw**: `MoveSim.inputDirection` reads `state.yaw`, so the host must set
`sim.state.yaw` from the brain's desired move heading each tick before
`update`. Combat facing (aim) is a separate field the fire path uses.

## Phase 2 — Real weapons, real projectiles

The piece that makes bots *visibly* legal: they fire the same projectiles
players do.

- Brain's `fire` carries `weaponType` chosen from a per-bot loadout
  (see Phase 4). Aim leads by `dist / stats.speed` + inherit-velocity
  (stats are in `WEAPONS` — speed/gravity/directDamage/aoeRadius all
  there; the current hardcoded `d/60` lead becomes `d/stats.speed`).
- **Server**: new `RoomProjectiles` (or extend CombatHandler's registry
  into a sim): server-side ballistic step `v.y += g*dt; pos += v*dt` at
  tick rate, `hmHeight` terrain contact → detonate via existing
  `processAOE`, capsule proximity (`pointToCapsuleDistance` already in
  shared) vs players → `applyHit` direct path, structure colliders via
  `structureColliders` (shared/ballSim.ts already has the OBB code).
  Broadcast `projectileCreated` at spawn (clients render it like a real
  player's shell) and `projectileDestroyed` on impact. The existing
  `botFire` becomes fallback only for hitscan weapons (Chaingun/Railgun
  semantics — decide per weapon: hitscan weapons resolve immediately
  through the same funnel with a real spread roll).
- **Client**: `GameBot` fires through the actual local projectile pool —
  `deps.projectiles`/fire path — so offline bots shoot real rockets with
  real arcs and the player's own explosion/claims machinery resolves
  hits. `resolveShot` dies; `combat.ts` already owns "projectile hit bot
  id" via `botHit`.
- Watch out: `Projectile` (client) is THREE-coupled — the server needs a
  shared ballistic step, not the renderable class. Add
  `shared/projSim.ts` (~40 lines: pos/vel/gravity/lifetime/hitRadiusAt
  reuse) rather than porting Projectile.

## Phase 3 — Belt + skills + energy

- `skill` intent → STATUS bits on the bot's PlayerState (server) /
  `p.status` equivalent (offline). The RoomMoveSim energy model already
  charges/drains on those bits — cloak/shield/mend work for bots for
  free once the bits flow.
- `belt` intent → item use: grenade = a lobbed projectile through the
  Phase-2 path; mine = `RoomDeployables`-style plant at feet; disc =
  belt-disc projectile. Brain triggers belt on cooldown: mine when
  defending a flag/base, grenade into clusters, disc-jump assist on
  chases (blow self forward = fun, keep rare).
- Energy gate: brain shouldn't ask for jet/cloak it can't afford — pass
  `energy` into `BrainCtx` so the sim's economy and the brain's intent
  don't fight.

## Phase 4 — Loadouts + roles

- Per-bot loadout rolled at spawn: `primary` (rocket/disc/mortar/
  chaingun/plasma…), `sidearm` (pistol/revolver/shotgun — used when
  target is close or primary on cooldown), `belt`, `perk` (join-time
  perk field exists — bots get one, RoomMoveSim already applies
  perkMods to drain/knockback).
- Range-band weapon select: mortar/flak at lob range, chaingun close,
  rocket/disc mid, railgun long-with-LOS. Put a `preferredRange` per
  weapon class in the brain and let the existing orbit-band logic use it.
- Kill feed `weaponType` already renders — bots get real weapon names for
  free once `playerKill.weapon` is the bot's loadout weapon.

## Ordering + risks

1. **Phase 1 first** — everything else composes on a legal body. Big
   visible win alone: bots ski/jet/fall like players.
2. Server tick cost: 9 bots × 60Hz MoveSim stepping inside a 20Hz tick —
   `sim.update(dt)` substeps internally, fine. The context-steering
   probes (16 slots × 2 getHeight) at think cadence are the hot spot —
   keep `THINK_S` and steer on the think tick, not every sim step.
3. Determinism: Math.random() in brains is fine (server owns truth for
   server bots; offline is local). Don't share RNG state across sides.
4. The correction loop: bots skip `reconcile` (they never report) — make
   sure `handlePosition` paths treat `isBot` like the ping exemption
   already does, or bots will get corrected by their own shadow.
5. `botFire` broadcast today bundles aim+hit in one message; real
   projectiles replace it — keep `botFire` only if clients still need a
   cheap muzzle/tracer cue for hitscan weapons.
6. Demos: server bots firing real `projectileCreated` events record into
   demos for free — one more reason to prefer real projectiles over
   synthetic bolt broadcasts.
