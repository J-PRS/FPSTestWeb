The biggest upheaval that's still *valuable* — not just big — is this one, and your own codebase has been pointing at it for weeks:

## Kill the claim layer. Make combat predict/reconcile, like movement already is.

Right now you run **two different authority models** side by side:

- **Movement**: client predicts → sends inputs → server sims → corrections. Server sims the truth.
- **Combat**: client sims → sends *outcome claims* (`shot`/`aoeShot`/`heal`/`envDamage`) → server re-derives and validates every claim against ledger/rewind/solids/rate gates.

The claim path is where your pain lives. Your own server log is a wall of it: `projectileId: invalid or oversized`, `flight blocked by structure`, `end 967m beyond reach`, `no known projectile — spawn claim never arrived`, `fire rate (flood)`, `dropped deferred claims`, `shotRejected` echoes. That's not tuning noise — it's a whole adjudication layer (`shotClaims`, `combatAoe`, `claimLedger`, defer/reject/notifyDrop, shotId nonces, spawn-vs-hit pairing) whose job is to *guess whether what the client already decided is legal*. It's the single largest source of netcode surface area in the game.

**The upheaval**: shots work like movement.

1. Client sends only a **fire intent** (weapon, dir, timestamp).
2. **Server sims the projectile authoritatively** — it already does this for remote replicas; `isRemote`/`tickRemote` exists.
3. Client **spawns a local predicted shell immediately** (identical shared sim — spawn pos/dir/vel are deterministic from the intent), renders its trail, plays its arc.
4. When the server broadcast lands, the predicted shell gets stamped with the real `projectileId` and reconciles — same reconcile model movement uses.
5. Hits are server-derived outcomes, never client claims. Lag comp already exists (`rewindPos`).

What dies: the entire `shot`/`aoeShot` claim surface — `claimLedger`, deferral, `validateAoeClaim`, `projectileId` wire plumbing, every "rejected" warn class, the 2.152 spawn-inheritance patch you just shipped. Probably ~2–3k lines of the most fragile code in the repo.

**The costs (honest):**

- Shot *spawn* gains up to an RTT of latency if you wait for the server shell — mitigated by the predicted shell, which is what games like this actually show anyway (the predicted arc is visually identical since the sim is shared and deterministic).
- Server CPU sims every live shell — bounded (TTL × fire rate × players), and your soak harness proves it: 16 bots, ~900k messages, zero strain.
- You lose "instant hit claim" responsiveness on direct hits — replaced by `playerHit` broadcasts ~half-RTT later, which is how every mainstream projectile game works anyway.

**Why it's the biggest *valuable* one**: it doesn't add capability, it deletes a whole *class* of bugs — every desync between "what the client claimed" and "what the server derived" becomes structurally impossible, because there's only one sim. It's also the only upheaval whose direction is *less* code.

## Runners-up (bigger scope, worse value)

- **Full lockstep/GGPO** — input-only netcode + state-hash healing. Maximal bandwidth/determinism purity, but you forfeit authority-by-construction and every desync becomes everyone's problem. You have a working authority model; this trades it away.
- **Sim-in-a-Worker** — moves jank, doesn't remove it; the worker boundary adds a serialization tax on the shared types.
