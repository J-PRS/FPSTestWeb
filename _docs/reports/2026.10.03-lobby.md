Yes — it violates the standard pattern. The web search mostly confirms what good lobbies already do: **per-match config is explicit and locked at match start**; user settings only *prefill* the form, they never act as a hidden parallel channel. Generalized, the precedence should be strictly layered:

```
explicit per-match pick  >  per-match/session state  >  user preference (prefill only)  >  spec/system default
```

Our code violates it twice:

- **`fps-mode` is doing three jobs** — solo ruleset, the solo-vs-online gate (`soloMode = !mode && !room && !p2p`), and a room-creation hint via the join handshake. A preference should never silently *become* match config.
- **The lobby's ANY isn't really ANY.** It deletes `?mode=`, which falls back through `urlParams.mode` to `fps-mode` — so "let the map decide" actually means "let my saved settings decide," but only when the map picker is also on "server default." (When a real map is picked, `dataset.mode` saves you — which is why it *usually* works and feels random when it doesn't.)

What established games do instead:

1. **Global settings contain only *defaults for the pickers*, labeled as such.** Halo/TF2-style: "Default gametype" prefills the host dialog; once the lobby opens, the global is out of the picture.
2. **The host dialog is the single source for the match.** Every field in it serializes into the join/create request verbatim — what's shown is what's sent. "ANY / MAP DECIDES" is itself an explicit value that resolves to the map spec *before* the request, not an absence that something downstream re-interprets.
3. **Match config locks at join.** The room, not the client's preferences, owns the mode after creation — which our server already does correctly; the bug is purely that the client sends a phantom hint.

Concrete decoupling for this codebase:

- Rename the settings row `MODE` → `SOLO MODE` and scope it: it controls offline boot only. It never enters `urlParams.mode`'s fallback for online joins.
- `urlParams.mode` getter stops reading `fps-mode` — split into `urlParams.mode` (URL only) and `settings.get('fps-mode')` consumed only by `main.ts`'s boot/solo path.
- Lobby: prefill `modeSelect` from `fps-mode` as a convenience (so your favorite mode is preselected), but always send an explicit mode — ANY resolves to the selected map's `dataset.mode` (already does) or sends nothing *and* the join handshake stops falling back to `fps-mode` entirely.
- The join message's `mode` field then means exactly one thing: the creation hint the lobby/user chose.
