## One correction: read the 47% WT datagram loss as a bug signal, not a verdict

The doc treats "~47% WT datagram loss on loopback" as evidence unreliable lanes
don't pay rent. Loopback datagram loss that high is almost certainly **our
stack dropping under backpressure** (Chrome drops WT datagrams when the sender
outruns the writable buffer — `datagrams.writable` backpressure is the app's
job). WS-only as the production baseline is still correct — but for
*operational-maturity* reasons (pion benchmark evidence above), not because
unreliable delivery is worthless. Keep Phase 8 honest: if it returns, gate it
on a fixed backpressure discipline first, and re-measure.

## Patterns the plan misses

### 1. Socket.IO "connection state recovery" — the offset cursor (slot into Phase 1)

Socket.IO 4.6+ ships the industrial version of reclaim: every server→client
packet carries an **offset**; the client stores the last processed offset with
its session id; on reconnect the client presents `(sessionId, lastOffset)` and
the server **replays only the missed packets** instead of resnapshotting.
`socket.recovered` tells the client which path it got.

Our edge-event model (`ballSegment`, `crawlEvt`, flag events) is a natural fit:
the reconnect path currently resyncs wholesale, but an offset cursor on the
ordered reliable stream would let grace reconnects just backfill — cheaper and
it preserves causality (client sees events in order, including ones it lost).
This is the same shape as Tribes' transmission-record delivery notification —
one cursor per session, persisted with the seat for `maxDisconnectionDuration`.

### 2. Photon Quantum "hard tolerance" — a fill policy for missing input (slot into Phase 3)

The doc's command-clock feedback fixes *clock drift*. It doesn't say what the
server does when an input for tick T simply never arrives — which is currently
"a drifting client gets commands dropped forever" (their own words).

Quantum's answer: after `HardTolerance` ticks the server stops waiting and
**fills the gap** — repeats the last known input (or nulls it), stamps the fill,
and confirms the tick-set back to clients with which inputs were real vs filled.
No stall, no silent drop — the client that missed packets sees `filled` flags on
its confirmation and knows it drifted. This converts our failure mode from
"player freezes until reap" into "player extrapolates, then gets a clockHint +
filled-marker telling it to resync." Same outcome, observed and recoverable.

### 3. Yojimbo state encoding — the machine is a projection, not a pile (naming/invariant for Phase 1)

yojimbo's `STATE-MACHINE.md` separates wire format from behavior-over-time and
encodes states so **negative = failure, zero = idle, positive = progress** —
predicates like `IsConnecting()` are thin reads over one number. Its hard
invariant is worth copying verbatim into the SessionRegistry: **"no transition
into CONNECTED that does not pass through CONNECTING"** — in our terms: no
path from `reaped` to `active` that skips `connecting`. That's exactly the
invariant the scattered stores can't express today and why stale-generation
callbacks slip through.

### 4. Input redundancy is a Phase-8-only artifact (ordering note, not new work)

Quantum's `SendRedundancy` (client resends the last K inputs staggered) only
exists to survive unreliable-lane loss. On WS it's pure waste — TCP already
redelivers. Don't build it in Phase 5's "unreliable class degrades to drop
stale seq" — the degradation is correct, but note the redundancy requirement
returns the moment Phase 8 reintroduces datagrams.

### 5. Grace is a *gameplay* decision, not just plumbing (new exit criterion for Phase 1)

Colyseus `onDrop` hooks deliberately leave the *room-side* semantics to the
game — whether the disconnected player holds the flag during grace is a design
call. Add to Phase 1's exit list: **grace-period gameplay semantics are
explicit** (carrier keeps flag vs drops it on drop, bot continues vs freezes).
Today it's whatever falls out of the reaper's order — the state machine is
where that decision should live and be logged.

## Amended sequencing

Same spine, three moves:

- **Phase 0.5 — WS-only now** (doc's Phase 2). Shrinks the surface the session
  rewrite must reason about. Cost: one env default + keeping listeners.
- **Phase 1 — add:** scenario suite written *against current behavior first*;
  offset-cursor reclaim (pattern 1); token-always-required reclaim (#962);
  yojimbo-style state encoding + the "no active without connecting" invariant;
  grace gameplay semantics decided explicitly.
- **Phase 3 — add:** hard-tolerance input fill + filled-markers on input
  confirmations (pattern 2), alongside the command-clock feedback.
- **Phase 8 — add precondition:** WT datagram backpressure discipline +
  re-measure before concluding anything about unreliable lanes.

Everything else stands: Phase 4 domain events, Phase 5 per-class delivery
guarantees (that's the enet channel model — one socket, per-message-class
reliability — worth reading enet's `protocol.c` as the reference
implementation), Phase 6 shared purity, Phase 7 observability.

## Post-landing addendum: a reject is a verdict, not transport loss (2026-10-03)

Soak evidence (4 bots, drop-every-12s + hop-every-15s + 5% loss): thousands of
`fire rate` rejects seeded by ~200 `implausible spawn` claims. Root cause
chain found by log, not guess: a refused spawn claim produces no
`projectileCreated` ack, so a loss-tolerant client's resend loop keeps
re-firing it — every resend re-ran the gates AND consumed a fire-window
slot, which rejected the next legit spawn, which joined the resend queue.
Cascade.

Two rules now encoded:

1. **`shotRejected` carries `shotId`** — a client that retransmits un-acked
   spawns MUST drop the refused claim on receipt. The verdict names the
   claim; without it the client cannot tell "rejected" from "lost".
2. **gameState is a resync boundary** — claims queued before it are stale
   the same way pre-hop claims are (the grace gap lets the server move the
   record unobserved). Purge pending spawn/shell claims on every gameState.

Validation: 3×30s soaks post-fix — zero rejects, clean reclaims, clean
closes; the old-build flood proved the anti-cheat gates were right and the
client queue was wrong.
