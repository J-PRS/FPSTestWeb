# Species registry overhaul — audit + landed work (2026-10-01)

## What was wrong

The creature system was already 80% data — five family modules each with
a `FAMILY_SIM` const + `FAMILY_SPECIES` tuning row + identical
`make*/step*/apply*Damage` triple — but the *binding* between species
and family was open-coded everywhere:

- **Six-way if-chains at every dispatch site.** `creatureSpawn.ts`
  (make + spawn-height, two chains), `creatureBrain.stepBody`,
  `CreatureSim` damage — same ternary chain duplicated 3×.
- **Family identity by duck typing.** `isFlyer = 'orbitPhase' in c` —
  a new family whose first field collided (`age`, `hitCd`, `animT`,
  `lockDist` were the discriminants!) would silently run the wrong sim.
- **Species row tables fragmented 6 ways.** Adding a species to an
  existing family was one row, but knowing WHERE the row went meant
  reading five files; adding a family meant editing every chain.

## Pattern

Type Object (Game Programming Patterns): a creature *has a* species
row rather than *is a* class. Same shape the client already uses for
render-side `SWARM_SPECS` and the same shape MELEE_SPECIES proved —
just unified. Family keeps owning behavior code (movement sims are
genuinely different); species owns tuning.

## Landed

- `shared/species.ts` — `SPECIES[species] = { family, speed, health,
  bite, blast?, aggro?, pounceD?, orbitR?, orbitAlt? }` + `speciesFamily()`.
- `shared/creatureSim.ts` — `SimBeing` union moved here;
  `isFlyer`/`isRoller`/`isSlither`/`isBaneling`/`isTotem` now narrow on
  the `c.family` literal (no more duck typing); `SPECIES_FAMILY` —
  `{make, step, damage, lift}` per family, the only binding site.
- Each `SimX` gained a `family: '<x>'` literal; each `make*` sets it
  and reads the unified row (same fallback semantics).
- `creatureSpawn`: `fam.make(...); c.y = gy + fam.lift(c)` — both
  chains gone. `creatureBrain.stepBody`: one table index.
  `CreatureSim` damage: one table index.
- Old per-family table exports (`MELEE_SPECIES`, `FLYER_SPECIES`, …)
  and `is*Species` predicates kept as derived views/shims — tests
  unchanged.

## Result

Adding a creature to an existing family = one SPECIES row (+ one
SWARM_SPECS entry for rendering). A new family = one sim module + one
SPECIES_FAMILY row — no dispatch-site edits.

## Verify

- `bunx tsc --noEmit` (server): clean; client tsc: clean.
- `bun test`: 736/736 pass — incl. the 33 creature-sim parity tests
  (authority vs predictor replay identical streams on every family).
- Client vitest: same 6 preexisting failures in other-agent files
  (settings/keybinds/ctfFlags/botFire) — untouched.
