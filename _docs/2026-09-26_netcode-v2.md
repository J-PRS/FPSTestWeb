# Netcode v2 — transport tiers + channel semantics

Status: IMPLEMENTED (WT + RTC client transports + RTC server peer live; WT server half pending). Ordering: WebTransport → WebRTC → WebSocket.

## Why

TCP head-of-line blocking is the ceiling on feel: one dropped position packet
stalls every packet behind it, so a player with 2% loss sees hitching even at
good ping. UDP-family transports deliver each packet independently — stale
position data can simply be dropped instead of delayed.

## Tiers

1. **WebTransport** (HTTP/3 datagrams over QUIC) — cleanest fit: unordered
   unreliable datagrams + reliable streams in one session, no signaling dance.
   Requires HTTP/3 cert setup on server; Safari can't connect yet.
2. **WebRTC DataChannel** (`{ordered:false, maxRetransmissions:0}`) — true UDP
   semantics, widest UDP reachability. Needs signaling (we already have
   RtcRelay) + `node-datachannel` on the Bun side. TURN needed for ~10% of
   hostile NATs.
3. **WebSocket** (Bun.serve, current) — always works; the safety tier.

## Channel semantics (the actual v2 work)

A transport alone buys nothing — the protocol must mark each message
reliable-ordered or unreliable-unordered, and consumers must tolerate gaps:

- **Reliable stream**: join/hello, shot/aoe claims, flag events, scoreboard,
  chat, deployable lifecycle, map spec. Sequence-checked.
- **Unreliable datagrams**: position frames, ball states, interpolated remote
  pose. Each carries a seq; consumer drops `seq <= lastSeq` (already the
  pattern in interpolation — extend to explicit seq).

## Shape

```
shared/transport.ts     NetChannel iface: sendReliable() / sendUnreliable(), onMessage
client/src/net/tiers.ts connect(): try WT → RTC → WS; attaches channel to NetworkManager
server_bun/src/tiers.ts Bun.serve WS (exists) + webtransport-bun + node-datachannel session adapter
```

## Landed (2026-09-26)

- `shared/netchannel.ts` — `NetChannel` iface + tier names.
- `client/src/networking/tiers.ts` — `TieredTransport` (NetworkManager's
  default factory), `WebTransportGameTransport` (datagrams = unreliable
  binary, one bidi stream = newline-delimited reliable JSON), and
  `ServerRtcTransport` (unordered+unreliable `game` DataChannel). Probes
  gated by `?net=wt` / `?net=rtc`; every failure falls through to WS.
- `server_bun/src/RtcServer.ts` — `/rtcs` WS signaling → `node-datachannel`
  PeerConnection → `RtcSocketAdapter` (DataChannel wearing the
  ServerWebSocket shape: send/close/readyState/data) → GameServer's
  existing onOpen/onMessage/onClose. Game code can't tell RTC from WS.
- `shared/wire.ts` — tick frames carry server `tickSeq` (u32 @6);
  NetworkManager drops `tickSeq <= lastTickSeq` (stale-drop in place for
  the day a UDP tier delivers out of order). PROTOCOL_VERSION = 10.
- `NetworkManager.sendBinary` → `sendUnreliable ?? send`.

## libdatachannel notes (verified by loopback test)

- `setLocalDescription('answer')` **segfaults** — call the no-arg form.
- Its answers contain `a=setup:actpass` (illegal); must be munged to
  `a=setup:active` before sending. RtcServer does this.
- Signaling is non-trickle: SDP goes out only at gathering 'complete'.
  No `addRemoteCandidate` path — remote candidates must arrive embedded.
- Client-side `maxRetransmissions` is `maxRetransmits` in the DOM lib.

## Still open

- WebTransport server half (`webtransport-bun`, HTTP/3 + cert story).
- STUN/TURN for hostile NATs (host-candidate answers are LAN/dev only).
- RTC reliable lane: the single datachannel is unordered — JSON events
  there can arrive out of order (acceptable today; a second ordered
  channel is the upgrade path).

All three produce the same `NetChannel`; Room/NetworkManager never see the
difference. First milestone: the abstraction + a loopback/WebSocket impl so
the seam compiles with zero behavior change; transports plug in after.

## Validation unchanged

Server stays authoritative — claims (shot/aoe/deploy) ride the reliable
channel, so the existing replay-window validation is untouched.
