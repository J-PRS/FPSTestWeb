## The original T1 remote-player pipeline — and its flaw

`ghostSetMove` on each server update:
1. Snaps to server pos/vel
2. **Predicts forward** `predictForwardTime + 32ms` by running real `updateMove` ticks
3. **Linearly blends** rendered pose → predicted endpoint over `interpolateTime` via per-ms `deltaPos/deltaTurn/deltaPitch`

So T1's original scheme was *predict-forward + chase the prediction* — which is exactly the class of algorithm we just replaced (and why it felt springy/oscillating). **Altimor's netXT replaced it with snapshot-buffered resimulation — the same bet we made.** We're in good company.

## T1 skiing: it's not a mechanic, it's an emergent property

The real `updateMove` reveals skiing comes from two things:

```cpp
// traction accumulates from collision surfaces:
t = surface.verticalDot * material->fFriction;   // flat=1.0, slope<1.0
// and collisions PRESERVE momentum:
dVel = surface.normal * (-dot + SurfaceShift);   // reflect, don't kill
lVelocity += dVel;
```

- **Traction = `verticalDot × friction`** — a 45° slope gives ~0.7× friction traction. You don't "ski" in T1; you just *can't grip* steep slopes, so gravity + the momentum-preserving collision response slides you downhill automatically. `UseFriction` is even cleared when desired-acceleration exceeds `maxAcc`.
- If our `movement.ts` treats skiing as a special friction mode rather than **traction-by-slope**, that's a fidelity gap — the authentic model is simpler and better-behaved.

## Other real mechanics worth stealing

- **Slope jumping is directional**: `jumpSurfaceNormal` (the last contactable surface's normal) drives jump impulse — `horizontal component toward input × dot + normal.z × jumpImpulse`. Jumping off a slope kicks you *along* it — slope-jump boosting is built in, not scripted.
- **Lateral jet locked for 8 ticks airborne** (`jumpSurfaceLastContact > 8`) — you can't strafe-jet on takeoff. And lateral jet force tapers as velocity approaches `maxJetForwardVelocity`, redirecting the remainder vertical — that's the T1 "jets follow your momentum" feel.
- **Server deliberately runs one move behind** — processes trigger from the *current* move but movement from `lastPlayerMove`: "faster firing, one extra lag step on movement." Intentional.
- **`updateDebt` anti-flood**: server processes ≤5 queued moves per tick; idle clients accumulate debt and get a synthetic empty move — elegant DoS/stall protection we don't have (our server just takes the latest update).
- **Wire format**: velocity as 17-bit magnitude + 10-bit normal, rotation 9 bits, energy 7 bits, `updateSkip` 4 bits — real bit-packing throughout.

## And the SFV fix's one transferable law

```cpp
Input->MaxFramesAhead = min(PingFrames + 1, 15);
TargetTimestamp = min(DesiredTimestamp, OpponentTimestamp + MaxFramesAhead);
```

**Never run your sim more than ~½RTT ahead of the opponent's last confirmed input**, with one-frame hysteresis (`PingFrames == LastPingFrames - 1` → keep old value) so ping jitter doesn't hitch. For us: cap local predicted-sim lead over the last server-acked state by ~½RTT rather than fixed — same symmetric-rollback fairness principle.

## What I'd actually port

In priority order for our codebase:

1. **Traction-by-slope skiing** in `movement.ts` — replace discrete ski mode with `verticalDot × friction` traction + momentum-reflecting collision. That's the "real" T1 feel, and it's *less* code than a bespoke ski state.
2. **`jumpSurfaceNormal`-driven slope jumps** — we track `lastJumpableNormal` already; the impulse math (directional horizontal kick + `normal.z` vertical) is the authentic version.
3. **Jet lateral lockout (~8 ticks) + velocity-tapered lateral force** — two constants and a dot product, big feel upgrade.
4. **`updateDebt` on the server** — flood protection is free.
5. Clock sync remains the structural one from the earlier list.
